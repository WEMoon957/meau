# 菌彩点餐智能体 — 技术路线与方法

> 本文档面向管理层，用通俗语言说明"小菌点餐智能体"是怎么做出来的、用了什么技术、为什么这样选、能带来什么价值。

---

## 一、一句话讲清楚这个项目是什么

**这是一位"会说话、懂菜单、能推荐"的 AI 点餐服务员**，顾客用大白话跟它聊天，它就能帮顾客查菜、配菜、推荐、下单，全程像跟真人服务员交流一样。

它不是冷冰冰的"按键点餐"机器，而是能听懂"我们 6 个人，要辣的，有老人，预算 500"这种自然语言的智能助手。

---

## 二、为什么要做这件事（解决什么问题）

传统点餐有几个老大难：

| 痛点 | 现状 | 我们解决后 |
|------|------|-----------|
| 顾客选择困难 | 菜单几百道，顾客翻半天定不下来 | AI 根据人数、口味、忌口一键配好一桌菜 |
| 服务员忙不过来 | 高峰期一桌等半天没人接待 | 顾客随时开口，AI 秒级响应 |
| 推荐不专业 | 服务员凭经验推荐，质量参差 | AI 懂搭配禁忌、懂营养、懂菌子相克 |
| 人力成本高 | 招人难、留人难、培训成本高 | 一套系统顶多个服务员，长期降本 |
| 数据沉淀难 | 点了什么、谁爱吃什么都没记录 | 每次对话都是数据，可分析可复用 |

**核心价值：用 AI 把"点餐"这件高频、重复、依赖经验的事，变成标准化、智能化、可规模化的服务。**

---

## 三、技术路线总览（我们怎么做的）

整个系统可以分成 **5 层**，从下到上像盖楼一样：

```
┌─────────────────────────────────────────┐
│  ⑤ 用户界面层  （顾客看到的聊天页面）        │
├─────────────────────────────────────────┤
│  ④ 服务接入层  （Nginx + 应用服务器）       │
├─────────────────────────────────────────┤
│  ③ 智能大脑层  （大模型 + 推荐引擎 + 知识库）│
├─────────────────────────────────────────┤
│  ② 数据存储层  （MySQL + Redis + 向量库）   │
├─────────────────────────────────────────┤
│  ① 基础设施层  （云服务器 + Docker 容器）    │
└─────────────────────────────────────────┘
```

下面一层一层用大白话讲。

---

## 四、各层详细说明

### ① 基础设施层 —— "房子和地基"

**用了什么**：阿里云 ECS 服务器 + Docker 容器化部署。

**人话解释**：
- 云服务器就像我们在云端租了一块地。
- Docker 就像把整个系统装进一个"标准集装箱"，不管搬到哪台机器都能直接跑，不用重新搭环境。
- 好处：搬家容易、扩容快、出问题能快速回滚到上一版。

---

### ② 数据存储层 —— "三个账本各管各的"

数据存三处，各司其职：

| 存储 | 存什么 | 人话类比 |
|------|--------|---------|
| **MySQL 数据库**（腾讯云 TDSQL-C） | 菜品名、价格、辣度、过敏原、库存等结构化数据 | 像"菜谱总账"，每道菜一行，查得准 |
| **Redis 缓存** | 顾客对话记录、限流计数 | 像"服务员的小本本"，记得快、忘得也快（30 分钟自动清理） |
| **ChromaDB 向量库** | 菜品知识、菌子相克、搭配禁忌等文档 | 像"智能图书馆"，能按"意思"找内容，不是按字面 |

**为什么要三个？**
- 菜品价格这种精确数据，必须用 MySQL，一分钱都不能错。
- 对话记录这种临时数据，用 Redis，读写快、用完即弃。
- 知识库这种"模糊查找"的数据（比如"吃完菌子不能配啥"），用向量库，能理解问题的意思，不是死板匹配关键词。

---

### ③ 智能大脑层 —— "项目最核心的部分"

这一层是 AI 真正"思考"的地方，包含三大块：

#### 1. 大语言模型（LLM）—— "会说话的大脑"

**用了什么**：DeepSeek（对话生成）+ 通义千问（文本向量化）。

**人话解释**：
- 大模型就像一个读过海量文本的"聪明大脑"，能听懂人话、能组织语言。
- 我们用了**两套模型分工**：
  - **DeepSeek** 负责"说话"——理解顾客意图、生成推荐理由、组织回复。选它是因为性价比高、响应快（5 秒左右出结果）。
  - **通义千问** 负责"阅读理解"——把菜谱文档变成数学向量，存进向量库，供后续"按意思查找"。这是阿里的成熟服务，1024 维向量，效果稳定。
- 两套模型各干各的活，互不干扰，谁合适谁上。

#### 2. 智能推荐引擎 —— "店里的老法师"

**人话解释**：
- 光有大模型还不够，大模型不懂我们店的"规矩"。
- 所以我们写了一套**推荐引擎**，把人工经验固化成规则：
  - 比如火锅必须先选锅底（不能只点菜不点锅）
  - 比如有海鲜过敏的顾客，含虾蟹的菜自动剔除
  - 比如小孩用餐不推辣菜
  - 比如菌子相克（吃完菌子不能喝牛奶等）
- 推荐时按"人数算份数、按口味筛菜、按忌口过滤、按评分排序、按品类搭配"五步走，保证推荐结果合理。

#### 3. 知识库问答 —— "店里的活字典"

**人话解释**：
- 顾客问"吃完菌子不能吃什么"、"这个菜辣不辣"这类问题，AI 需要查资料回答。
- 我们把菜谱、食材知识、搭配禁忌等文档**预先"喂"给向量库**，顾客一问，系统按"意思"找到最相关的几段内容，再让大模型组织成口语化回复。
- 不是死板的关键词匹配，而是真正"理解"问题。

---

### ④ 服务接入层 —— "前厅和调度"

**用了什么**：Nginx（反向代理）+ Gunicorn + FastAPI（应用服务器）。

**人话解释**：
- **Nginx** 像餐厅的"迎宾员"，所有进来的请求先到它这里，它负责分流、挡恶意访问、转发给后厨。
- **Gunicorn** 像"后厨主管"，管理多个"厨师"（worker 进程）同时干活，一个忙了就交给另一个。
- **FastAPI** 是"做菜的具体流程"，定义每个接口怎么处理。
- 好处：高峰期多个顾客同时点餐，系统能并行处理，不会一个一个排队等。

**高并发能力**：单台服务器配置 4 个 worker，每个 worker 同时处理 20 个对话，理论可支撑 80 个并发会话，够大多数门店高峰使用。

---

### ⑤ 用户界面层 —— "顾客看到的门面"

**用了什么**：HTML 单页 + 聊天式交互。

**人话解释**：
- 顾客打开网页就是一个聊天框，像微信聊天一样发消息、收回复。
- 推荐结果以"菜品列表 + 总价 + 推荐理由"的形式展示，清晰直观。
- 支持多轮对话，顾客可以追问、调整、加菜。

## 五、我们特别看重的几件事（技术亮点）

### 亮点 1：安全第一 —— 防 SQL 注入、防滥用、防泄密

| 风险 | 我们怎么防 |
|------|-----------|
| 黑客通过输入恶意内容窃取数据库 | **彻底废弃"AI 写 SQL"方案**，改用参数化查询，用户输入永远不直接拼进 SQL |
| 接口被刷爆（DDoS） | Redis 限流：单 IP 每分钟 60 次、单会话 30 次，超了直接拒绝 |
| 跨域攻击 | CORS 白名单机制，只允许指定网址访问 |
| 敏感信息泄露 | 数据库密码、API Key 全部放环境变量，不进代码仓库 |
| 慢查询拖垮系统 | 每条查询强制 5 秒超时 + LIMIT 限制，防止全表扫描 |

**核心原则：宁可慢一点，也不能不安全。**

---

### 亮点 2：高可用 —— 系统不容易挂

- **健康检查**：系统每 30 秒自检一次（数据库、Redis、知识库），发现问题自动告警，负载均衡能自动把流量切走。
- **优雅降级**：知识库万一加载失败，推荐功能照常工作，不会整个系统崩。
- **优雅关停**：发版重启时，正在进行的对话能聊完再退出，不会让顾客话说到一半被打断。
- **自动重启**：容器挂了自动拉起，不用人盯。

---

### 亮点 3：会话隔离 —— 不会"串号"

**人话解释**：
- 多 worker 部署时，最怕 A 顾客的对话记录被 B 顾客看到（业内叫"会话串号"）。
- 我们把所有对话记录统一存在 Redis 里，按 session_id 物理隔离，A 和 B 的数据像两个保险柜，钥匙不一样，绝对打不开对方的。
- 这是很多团队踩过坑的地方，我们从架构层面就堵死了这个口子。

---

### 亮点 4：双模型分工 —— 性能与成本的最优解

| 任务 | 模型 | 为什么选它 |
|------|------|-----------|
| 对话生成 | DeepSeek-v4-flash | 响应快（5 秒）、成本低、中文表达流畅 |
| 文本向量化 | 通义千问 text-embedding-v3 | 阿里成熟服务、1024 维、稳定可靠 |

如果全用一个大模型，要么贵要么慢。分开干活，各取所长。

## 六、部署架构（系统怎么跑起来的）

```
        顾客手机/电脑
             │
         ┌───▼───┐
         │ Nginx │  ← 80 端口，对外唯一入口
         └───┬───┘
             │
     ┌───────▼───────┐
     │  Gunicorn (4个worker)  │
     │  FastAPI 应用 │  ← 3000 端口，仅本机访问
     └───┬───────┬───┘
         │       │
    ┌────▼──┐ ┌──▼──────────┐
    │ Redis │ │ 腾讯云 MySQL │
    │ (本地)│ │  (TDSQL-C)  │
    └───────┘ └─────────────┘
         │
    ┌────▼──────┐
    │ ChromaDB  │  ← 知识库向量存储（本地文件）
    └───────────┘

    对外调用：
    ├─→ DeepSeek API（对话生成）
    └─→ 通义千问 API（文本向量化）
```

**部署方式**：Docker Compose 一键拉起，nginx + app + redis 三个容器协同工作。

## 八、成本构成（领导关心的钱）

| 项目 | 月费用估算 | 说明 |
|------|-----------|------|
| 云服务器（ECS） | 约 200-400 元 | 2 核 4G 起步，可按需升配 |
| 云数据库（TDSQL-C） | 约 100-300 元 | 按用量计费，可Serverless |
| DeepSeek API | 按调用量 | 百万 token 约 1-2 元，门店日均几十次对话，月成本极低 |
| 通义千问 API | 按调用量 | 知识库构建一次性消耗，后续查询量小 |
| Redis | 0 元（自建容器） | 不用云服务，省一笔 |
| 域名 + SSL | 约 100 元/年 | 可选 |

**总体月运营成本可控制在 500-800 元**，远低于一个服务员的月薪。规模放大后边际成本更低。

## 九、下一步规划

1. **短期（1-2 个月）**：打通收钱吧支付，实现"推荐→下单→支付"闭环；接入真实门店菜单数据。
2. **中期（3-6 个月）**：多门店多租户支持，一套系统服务多家门店；用户画像积累，做个性化推荐。
3. **长期（6 个月+）**：接入语音识别（顾客直接说话点餐）；打通后厨打印、KDS 厨显系统；数据分析报表辅助经营决策。
